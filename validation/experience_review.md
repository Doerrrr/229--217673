## 适用范围修正

“附加业务条件一定能降低 T1”在本题已有反例。没有操作轨迹时，不能
猜测模型走了哪个捷径。不能靠隐藏条件、重复扣分、缩短时限或运行失败
制造低分。简单追加功能与重新设计任务主体是不同假设。

V3 改为公开的防泄漏发布任务，核心交付是化学连通分簇和三目标精确
全局匹配。参考解使用残量最小费用流，验证器使用独立 Hungarian 算法；
两者均经 500 个小图穷举核对。验证器按业务分配六类独立权重，不将
匹配报告或匹配 CSV 的语义错误重复扣到化学/正例检查。

## 经验状态与写入限制

### EXP-ddi-preflight-git-eol（跨平台保护哈希返修）

2026-10-11，用户在远端同步批准题包 `8023f518` 时，文件边界检查通过，
但 `check_release_assets.py --platform` 报 drug_list.csv 哈希不符；该轮
尚未提交或推送，也未触发平台检测。

本地核对确认原常量取自 Windows CRLF 工作文件，Git blob 和远端 Linux
预期使用 LF。三份 CSV 的工作字节仅将 CRLF 换成 LF 后，与批准提交的
Git blob 完全相等；工作流没有这项差异。保护脚本遗漏换行表示，不是
已证实的数据被更改。用户远端具体字节仍由恢复命令的固定哈希检查核对。

修复只改作者预检及交付说明，固定原 Git blob 的 SHA-256，仅在内存中
允许 CSV 的 CRLF/LF 表示差异；保留 Git 原始 CSV/工作流无差异保护。
自测验证三份文件的 LF、CRLF 均通过，内容字节改动、追加空格和 lone CR
均拒绝。参考解、候选环境、评分器、原始数据、输出摘要和工作流不改。
预检成功不代替 Harbor 或平台通过；旧 Harbor CI 未运行此作者预检，
所以它不能证明跨平台交付检查正确。

恢复必须从已暂存状态继续，先核对暂存题包仍与批准 SHA 一致，再只更新
预检文件；不能直接重跑要求干净目录的旧脚本，也不删除断言或现场重算
不可信数据的“预期”哈希。证据入口：本节、verification.md、Git EOL
与 blob 字节比较、预检 --self-test。状态：本地检查支持；远端恢复待回执。

证据来源：用户提供的 R1 报告及本地 SHA-256、Git blob 核对。

本轮删除隐藏参考侧启动器，参考脚本仅替换 Python 实现并复用候选入口；
新增发布前完整重复扫描及能拒绝重复文件的负向自测。目录创建、CSV
边界和缺参数场景正式进入已有检查，不增加权重或增难业务条件。
本地验收见 `local_results.json`、`verification.md`；最终 SHA 的 Harbor
结果须独立核对。后续平台 R1=97 已证实边界返修通过；第三版 T1=0.900 未达标。

这修正了助手此前只核查算法与奖励、遗漏重复文件边界的检查缺口。
